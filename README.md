# JOBIA — CLI local et distant

Python ≥ 3.10. Référence du serveur : [document maître Aurora](../AuroraIA/ARCHITECTURE_MAITRE.md#cli). Les moteurs ont leurs propres contraintes ; leur disponibilité sur tous les OS n'est pas garantie.

```bash
git pull --ff-only
./install.sh
jobia
```

Sous Windows : `.venv\Scripts\python.exe` et `.venv\Scripts\jobia.exe`. `install.sh` / `install.ps1` utilisent le même installateur Python. `jobia`, `jbia` et `aurora` exposent le même client.

Interface Aurora : `jobia` ou `jobia ui` ouvre l'interface plein écran ; un pipe affiche le tableau d'accueil. Conversation, plan, critères, preuves, fichiers reçus, skills, MCP et journal suivent les événements réels. Ctrl+K palette, F2 thème, F3 modèle, F4 vue, F5 diagnostic, Ctrl+C arrêt, Ctrl+Q sortie (une mission distante continue sur le PC), `/connect` appairage. `jobia ui --text` conserve le parcours linéaire. Huit thèmes déclaratifs : `otter` (défaut), `jobia`, `abyss`, `plain`, `phosphor`, `brutal`, `glacier`, `synthwave`. Options globales : `--theme`, `--color auto|always|never`, `--animation auto|full|reduced|none`.

Le panneau « Activité observée » reste visible sur les petits terminaux : étapes horodatées à réception, outils, preuves et fichiers. La sortie reçue s'affiche pendant l'exécution, sans être présentée comme un résultat confirmé. Après 15 secondes sans avancée, une alerte distingue une connexion vivante d'une absence de nouvelles ; un heartbeat ne prouve pas que le moteur travaille. Le texte et le journal sont rafraîchis par lots, avec un aperçu limité aux 16 000 derniers caractères.

```bash
jobia --theme jobia --animation reduced preview jobia
jobia connect --server https://ADRESSE_DU_SERVEUR
jobia doctor --remote --json
jobia mission "Inspecte ce projet et prépare un plan"
```

`mission` exécute une tâche sur le serveur (ou en local via `--host local` / repli avant acceptation avec `find_files`, `search_code`, `git_status`, `list_skills`, `read_skill`, `revise_plan`) ; `run` pilote une boucle locale d'amélioration. Une erreur de mission produit un code de sortie non nul. Les fichiers reçus sont contrôlés par taille et SHA-256. Le journal du serveur survit au redémarrage du bridge. `jobia missions list`, `jobia missions status ID`, `jobia missions stop ID`, `jobia missions local`, `jobia missions watch ID` et `jobia missions resume ID [--model ...]` permettent de retrouver, inspecter, arrêter, suivre et reprendre le même objectif. `jobia agents list|enable|disable|inspect|create|delete`, `jobia mcp list|tools|call` et `jobia skills list|read|create|discover` pilotent le registre d'agents, les outils MCP et les skills du bridge. Dans l'interface : `/attach ID`, `/resume ID`, `/retry` pour une acceptation incertaine avec la même clé d'idempotence. Une action de résultat inconnu doit être inspectée avant rejeu.

`/clear` remet l'interface à zéro et efface les conversations locales du dossier courant. Depuis le terminal, `jobia clear` fait le même nettoyage et `jobia clear --all` inclut tous les dossiers. Les archives sont déplacées dans une sauvegarde locale dont le chemin est affiché ; les missions distantes, les fichiers produits et la configuration restent conservés. `/new` ouvre simplement une nouvelle conversation en gardant les précédentes. Après un nettoyage depuis un autre terminal, redémarre les interfaces déjà ouvertes.

Configuration privée selon les conventions de l'OS, surcharges `JOBIA_CONFIG_DIR` / `JOBIA_DATA_DIR`, migration des anciennes configurations Aurora sans écrasement. Adresse : argument, `JOBIA_SERVER_URL`, `AURORA_SERVER_URL`, configuration ; clé : `JOBIA_API_KEY`, `AURORA_API_KEY`, configuration. Sans autorisation mémorisée, `jobia connect` affiche un code court à saisir dans la fenêtre du PC. L’autorisation reçue est mémorisée automatiquement, jamais affichée ; aucune clé à obtenir manuellement. Les anciennes clés autorisées restent compatibles et ne doivent pas être publiées.

`doctor` contrôle le client local ; `doctor --remote` vérifie aussi le daemon et sa capacité à accepter une mission. Un contrôle positif ne prouve pas la qualité d'une génération ou le trajet SSE public. La readiness des moteurs est distincte de leur simple présence sur disque.

Le serveur conserve l'objectif original, découvre les scripts des modules, mène des expériences, charge les skills, crée des rôles persistants et exécute des tâches de workers avec concurrence configurable. Après une modification, une fin de mission nécessite des contrôles concrets ; une revue LLM de la couverture complète ces mesures sans les remplacer. Ollama utilise ses options natives ou `AURORA_MODEL_OPTIONS` explicite, et les durées/débits viennent du moteur. Les permissions directes sont contrôlées ; les commandes autorisées utilisent encore le shell de l'hôte sans sandbox OS. Aucun comportement AGI ni absence universelle de bugs n'est établi.

`./install.sh` installe aussi le renderer natif compilé sur GitHub, avec contrôle SHA-256 et version, sans Cargo sur le Mac. `jobia` ouvre directement l'accueil, y compris avec une mission conservée : les avis de reprise restent visibles sous le dessin, sans relancer le travail. Otter est le thème par défaut ; un autre choix enregistré reste respecté. Aucun choix de renderer, commande de thème ou export de variable n'est requis pour démarrer. `/home` retrouve l'accueil sans effacer l'historique. Le moteur reste Python ; le repli `jobia ui --renderer python` fonctionne sans binaire natif. Voir [installation et tests](docs/CLI.md), [thèmes](docs/THEMES.md), [design et mesures](docs/DESIGN.md), [protocole](docs/PROTOCOL.md). Ces documents concernent le CLI ; les moteurs restent régis par le document maître.

MCP (1.5.4) : `jobia mcp catalog SERVEUR --kind tools`, `resources SERVEUR`, `prompts SERVEUR`, `read SERVEUR URI`, `prompt SERVEUR NOM --json-args '{"argument":"texte"}'` et `close SERVEUR`. `jobia mcp call SERVEUR OUTIL --json-args '{}' --timeout 120` affiche la réponse réelle. Une configuration `persistent: true` conserve l’état du processus serveur entre les appels ; fermer explicitement après avoir inspecté une action de résultat inconnu. Les missions locales disposent des mêmes catalogues et ne rejouent pas automatiquement un appel dont la réponse a été perdue. Ces commandes exigent un bridge connecté et des permissions d’exécution.

Preuves JSON (1.5.5) : les missions locales disposent de `verify_json_evidence`. Des pointeurs relient les champs du fichier sauvegardé aux reçus réussis de la même mission, avec égalité typée ou inclusion textuelle et décodage JSON explicite. Une contre-vérification échouée retire le crédit du critère. Ce contrôle couvre seulement les liaisons fournies : il ne garantit ni la vérité externe, ni la fraîcheur, ni la couverture entière de la demande. Les missions distantes utilisent `verify(kind="json_evidence")` du serveur compatible.

La version 1.5.6 précise les erreurs de pointeurs JSON : `/field` et `/items/0`, depuis le reçu complet ; la notation pointée ou à crochets est refusée. Un champ absent indique les clés disponibles, sans afficher leurs valeurs.

La version 1.5.7 demande aussi au décodage structuré une racine vide ou un préfixe `/`, avec une forme de schéma testée sur le moteur local. Le vérificateur contrôle encore la syntaxe complète et le contenu des reçus : un préfixe correct ne prouve pas que le chemin ou la donnée sont justes.

Preuves consultables (1.6.0) : `jobia missions evidence ID --tool browser_action` liste les reçus conservés ; `--evidence-id RECU --pointer /result` lit un reçu et ses vrais chemins JSON. Filtre, `--offset` et `--limit` permettent de parcourir le journal sans relancer les outils. Les missions disposent aussi de `inspect_evidence`, y compris en SAFE. Ces données sont historiques et bornées ; leurs troncatures sont explicites. Les vérifications doivent citer le reçu d’origine. Lors d’une reprise, le terminal affiche désormais le contexte retenu par le serveur, ou son absence de métadonnées, au lieu de présenter les défauts du client comme appliqués.

Références observées (1.6.1) : les schémas des missions locales utilisent les vrais identifiants des reçus conservés. `verify_json_evidence` accepte des `expressions` facultatives, dont `len(data["items"]) == 2` pour une quantité demandée. Seul cet intrinsèque JSON est admis comme appel ; les liaisons doivent encore vérifier chaque élément et leur distinction si elle est exigée. Les missions distantes bénéficient des vues de reçus et du contrôleur corrigé sur un serveur compatible ; ces contrôles ne garantissent pas à eux seuls la réussite d’une mission entière.

## JOBIA 1.7.0 — connexion qui se répare seule, MCP et skills intégrés, interface plus visuelle

**Connexion.** Quand Aurora redémarre, son tunnel change d'adresse : le client la retrouve seul, sans `jobia connect`. La publication `aurora-live` est lue au commit courant (annonce Git non mise en cache, puis fichier adressé par ce commit), avec repli sur l'API GitHub (ETag, un 304 ne consomme pas de quota) et sur le fichier de branche. Toutes les requêtes suivent le PC : lectures rejouées librement, lancement de mission rejoué avec sa clé d'idempotence (le bridge renvoie la même mission), écritures rejouées seulement si le bridge ne les a jamais reçues ; une mission acceptée ne change d'hôte qu'après confirmation par la nouvelle adresse. L'interface surveille la connexion (sonde légère toutes les 20 s, nouvel essai à 2, 4, 8, 15 puis 30 s), affiche une pastille d'état et un compte à rebours, puis se reconnecte et le signale. Une mission interrompue par le redémarrage reprend automatiquement depuis son checkpoint (deux fois au plus ; `jobia config auto_resume false` le désactive). `/connect` affiche le code d'appairage dans l'interface : plus besoin de la ligne de commande, y compris après une autorisation révoquée.

**Interface.** Bandeau d'état avec pastille animée seulement pendant un vrai travail, onglets segmentés (Conversation, Modules, Agents, **Skills**, **MCP**, Bilans, Journal, Fichiers), palette **Ctrl+K** avec recherche floue (commandes, vues, thèmes, skills, outils MCP, modèles), notifications, jauge de critères colorée, touches en relief, carte d'appairage à grands chiffres. Les deux renderers (Python et Rust) partagent ces éléments et une seule horloge d'animation ; au repos, aucun rafraîchissement. Rien n'est plus refusé pendant une mission : une nouvelle demande est mise en file (`/file`), `Ctrl+Q` ou `/new` détachent la mission distante (elle continue sur le PC, `/attach ID`), le modèle peut être changé pour les missions suivantes.

**MCP.** `jobia mcp import` reprend les serveurs de Claude Desktop, Claude Code, Cursor, VS Code, Windsurf, Gemini CLI et Codex (ou d'un fichier/URL) ; `jobia mcp search TEXTE [--registry]` cherche dans les outils, prompts et ressources connus et dans le registre officiel MCP ; `jobia mcp install NOM` installe un serveur du registre (npm, PyPI, Docker ou point d'accès distant) ; `add/remove/enable/disable/refresh`. Un serveur local s'exécute sur cet ordinateur (stdio, HTTP Streamable, ancien SSE), les autres noms vont au bridge ; `--local/--remote` forcent le côté. Les missions locales utilisent les mêmes serveurs. Dans l'interface : `/mcp`, `/mcp chercher`, `/mcp import`, `/mcp install`, `/mcp appel SERVEUR OUTIL {json}`.

**Skills.** Bibliothèque locale (`.aurora/skills`, `.claude/skills`, `~/.aurora/skills`, `~/.claude/skills`) : `jobia skills import SOURCE` (dossier, archive `.zip`/`.skill`, URL d'un `SKILL.md`, dépôt GitHub `owner/repo` ou `…/tree/branche/chemin`), `search` (accents et casse ignorés, quelques équivalences français→anglais, catalogue `anthropics/skills` avec `--catalog`), `create`, `remove` (sauvegarde datée), `enable/disable`. Dans l'interface, `/skill NOM` joint ses instructions (bornées) aux prochaines demandes, locales ou distantes ; un skill pertinent est suggéré sans être imposé.

**Sans garde-fou bloquant.** Les nouvelles configurations utilisent `FULL` ; `/permissions` ou `jobia permissions NIVEAU` restreignent à tout moment. Restent actifs, car ils ne bloquent aucun usage légitime : une mission choisie en `SAFE` refuse aussi les commandes et écritures côté client et l'exécution de code des hypothèses ; un fichier livré ne peut pas écrire dans `.git`, `.ssh`, `.env` ou d'autres magasins d'identifiants ; l'adresse publiée doit être un tunnel `trycloudflare.com` et un HTTPS est exigé hors réseau local pour l'appairage.

**Systèmes.** Renderer natif pour Linux ARM64 et Linux musl statique (toute distribution x86_64, Alpine, glibc anciennes) en plus de macOS, Linux x64 et Windows x64 (Windows ARM via x64) ; l'installateur essaie les variantes dans l'ordre. Sans `ensurepip` (Debian/Ubuntu sans `python3-venv`), l'installateur crée l'environnement avec uv, virtualenv ou un amorçage de pip, sinon il indique le paquet de la distribution détectée ; fish est pris en charge ; les scripts fonctionnent sans curl (wget) et installent uv si aucun Python n'est présent. Démarrage du CLI environ deux fois plus rapide (imports différés) et connexions keep-alive réutilisées entre les actions de l'interface.

**Preuves et limites.** Tests locaux : suite Python complète, tests Rust (`fmt`, `clippy -D warnings`, `test`), validations PTY des deux renderers contre un faux bridge en boucle locale (coupure, reprise, arrêt, aucun octet émis au repos). Transports MCP HTTP/SSE testés contre un serveur local ; stdio contre les serveurs de test du dépôt ; import réel du dépôt public `anthropics/skills` ; lecture réelle de la publication `aurora-live`. Non testé ici : un redémarrage réel du PC et de son tunnel, une mission sur le vrai serveur, l'exécution des paquets MCP tiers, les nouvelles cibles natives (construites par la CI à la prochaine release) et les terminaux physiques Windows/macOS.
